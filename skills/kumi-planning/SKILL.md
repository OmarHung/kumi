# 用 Kumi 規劃與追蹤工作

這份 skill 決定**東西放在哪裡、用什麼結構**；指令怎麼下、哪些寫入要先問，照 `kumi` skill（同一個 repo 的 `skills/kumi/`）。開始前先讀它，兩份要一起用。

結構的好壞決定之後追不追得動：放錯專案、一個項目掛三個人、進度寫在留言裡，系統就算記了也看不出誰卡在哪裡。所以你的工作不只是把字打進去，而是讓每一件事都有人、有日期、看得出在等誰。

## 先判斷是哪一種情況

| 使用者在做什麼 | 例如 | 照哪一節 |
|---|---|---|
| 導入或重整 | 「我們要開始用」「從 monday 搬過來要怎麼分」「現在的專案很亂」 | 導入：從業務到結構 |
| 開一個新案子 | 「接了一個新案子」「客戶 B 要做電商」 | 導入的第 2 到 4 步，問答用「新案子」那一套 |
| 記一筆或一批需求 | 客戶來信、會議結論、需求文件、口頭交代的事 | 記需求 |
| 檢視進度 | 「這週有什麼卡住」「幫我看 WEB 的進度」「現在做到幾成」 | 定期檢視 |
| 案子要結束 | 「這個案子做完了」「WEB 要結案」 | 結案 |

不確定時直接問使用者是哪一種，不要每一種都做。

## 五條項目的規矩

這五條是整份 skill 的核心。提案、記需求、檢視時都照它們判斷，跟使用者說明時也講理由，不要只丟規則。

1. **一個項目一位負責人，就是做的人。** 掛好幾個人，最後就沒有人負責。要盯的人在網頁上按「關注」；要別人做其中一段，開下層任務指派給他。系統刻意不支援多位負責人。
2. **項目要小：一個人一兩週內做得完。** 做不完就拆成下層。一個項目包了十個網站，哪幾站做完了只能去讀留言；拆成十個下層，進度一眼就看得到。
3. **「說明」寫要做什麼、怎樣算完成。** 討論放留言，有結論就回寫進說明。之後接手的人只讀說明就知道要交什麼。
4. **每一項都有到期日。** 沒有日期的事排不進行事曆與時間軸，也永遠不會出現在過期清單裡，拖多久都沒人發現。工時用「估計」（預估幾小時）與自訂欄位 `actual_hours`（實際工時）。
5. **狀態要看得出在等誰。** 「等客戶」和「內部驗收」（等自己人）分開，主管才知道該催誰。暫停的放 `backlog` 類別，仍算沒做完；不做的改成取消，不要刪掉，紀錄才留得下來。

結構的細節（專案怎麼分、什麼時候開類型、狀態與欄位怎麼設、常見的錯誤）在 [references/structure.md](references/structure.md)；內建的 12 個模板在 [references/templates.md](references/templates.md)。導入或要改專案設定之前，兩份都先讀。把需求寫成項目的規則（標題、說明的格式、負責人、日期）在 [references/capture.md](references/capture.md)，記需求之前先讀。

## 先看系統裡已經有什麼

動手之前先盤點，不要在已經有合適專案的地方另開一個：

```bash
kumi project list --json                             # 有哪些專案、哪些封存了
kumi blueprint export -p <代號> --format json        # 那個專案的類型、狀態、欄位（含選項的 key）
```

- 已經有的欄位與選項照用。例如「客戶」單選已經有某個客戶的選項，就用那個 key，不要再開一個同名的欄位。
- 要跨專案加總的欄位用同一個 key，例如工時一律是 `actual_hours`。key 不同，之後就加不起來。

## 問答：先確認、再問

資訊不夠寫出提案或項目時，先用問答補齊。每一輪是一則訊息，依序三段，使用者一次看完、一次回覆：

```markdown
### 我查到的，請確認
- <事實>（出處：<來信第 2 點／系統裡 MNT 的「客戶」選項／Excel 的 C 欄>）

### 打算建立的（草稿，建議的答案已經套進去）
<記需求是項目表；導入與新案子是提案。這一輪先只問時省略這段>

### 要問你的
1. <問題>
   建議：<你建議的答案，加一句理由>
```

- **查得到的也要確認，但不要重新問一次。** 從資料或系統讀到的，寫在「我查到的」並附上出處，請使用者確認或更正。資料可能過時、來信的說法可能不精確、系統裡可能有名字相近的兩筆；這時確認一次，比事後改錯省事。使用者回「都對」就照用，只更正的那幾條照他說的改。
- 「我查到的」只列會寫進系統、或會影響結構的：客戶、期限、金額、範圍、負責人、已經有的專案與欄位、相近的項目。只是背景的不必列。相近的項目已經過期或很久沒動時，在那一條寫出來，使用者可能要順便處理。
- 「要問你的」只放資料與系統裡都查不到的。一輪最多 5 題；已經有文件或來信時，通常 1 到 3 題就夠。**會推翻整個做法的前置問題放第 1 題**，例如是不是已經記過的同一件、要不要另開專案。
- 每題附建議答案，使用者可以只回「照建議」或「第 2 題改成…」。有選項的就列出選項、標出建議的那一個；真的有取捨的，每個選項附一句差別。不要問「你覺得呢」這種開放式的問題。
- **能先做草稿就附上草稿。** 前置問題不會推翻做法時，把建議答案套進去，附上「打算建立的」；使用者回「照建議」，一輪就結束。前置問題可能推翻做法時（例如可能和既有的項目重複），這一輪先只問，下一輪再給草稿。不論哪一種，使用者同意之前什麼都不建立。
- 問到寫得出這三樣就停：**怎樣算完成、負責人、到期日**。其餘還不清楚的，記進說明的「待確認」一段，先建項目，不要一直追問。
- 最多兩輪。第二輪之後還缺的，一樣記成待確認，回報時列出來。

### 題目

挑跟情況有關的問，已經知道的跳過。

**導入**（問整個團隊；開頭說明「不確定的可以跳過，我先照常見的做法提案」）
1. 你們做哪幾種工作？例如接案建置、維護合約、內部的事。各舉一兩個最近的例子。
2. 大概幾個人做？誰負責盯進度？客戶會不會進系統看？
3. 一件事從進來到結束會經過哪些關？哪幾關是在等別人（客戶、主管、廠商）？
4. 你或主管每週想看什麼？例如哪些過期、哪些在等客戶、每個客戶這個月花了多少工時。
5. 現在用什麼記？最困擾的是什麼？

**新案子**
1. 要交付什麼？有報價單、合約或需求文件可以給我看嗎？
2. 上線日或交付日是哪天？有沒有分期，或中間要給客戶看的日子？（建議：每一期開一筆需求，要給客戶看的日子在網頁上建成里程碑）
3. 客戶那邊誰驗收、誰點頭？客戶要不要進系統看？
4. 我們這邊誰負責整個案子、誰會參與？
5. 要不要追工時？（建議：要，任務填估計與實際工時）
6. 上線後的維護要不要接？（建議：接的話，上線後的修改記到維運專案，這個案子結案後封存）

**模糊的需求**（寫不出「怎樣算完成」時）
1. 要做到什麼程度？例如只評估與報價、先做最小可用的版本、完整做完。
2. 怎樣算完成？由誰確認？
3. 客戶要什麼時候？我們的到期日要不要提早，留驗收的時間？
4. 誰做？
5. 跟系統裡哪一筆有關？查到相近的項目就列在「我查到的」，問是不是同一件、要不要掛在它底下。

## 導入：從業務到結構

### 1. 了解業務

照「問答」的做法，題目用「導入」那一套。使用者有現成的資料（試算表、monday 的看板、需求文件、合約清單）時，先讀資料，把讀到的寫成「我查到的」請他確認，再問資料裡看不出來的。使用者回答一部分就可以先提案，其餘在提案裡標成「要你決定的」。

舊資料是 Excel 或 CSV 時，沒有專用的匯入器（monday 才有）：讀檔案（`.xlsx` 讀不了就請使用者另存成 CSV），照「記需求」的規矩整理成一張項目表，使用者確認後再一筆一筆建。已經做完的舊項目通常不必搬，問使用者要不要。

### 2. 對應成結構，寫成提案

照 `references/structure.md` 決定專案、類型、狀態與欄位，盡量用內建模板（`references/templates.md`），只改真的不合的地方。提案一律用這個格式，讓使用者一次看完、一次回覆：

```markdown
## 提案：<範圍，例如「接案與維運的導入」>

### 我從資料與系統看到的，請確認
- <事實>（出處：…）

### 專案
| 代號 | 名稱 | 模板 | 放什麼 | 為什麼這樣分 |
|---|---|---|---|---|

### 每個專案要改的設定
- <代號>：<要加或改的類型、狀態、欄位與選項；照模板就寫「照模板」>

### 先建立的項目
<代號>
- <類型>：<標題>（負責：<人或「待定」>，到期：<日期或「待定」>）
  - <類型>：<標題>（…）

### 你要在網頁上做的
1. …

### 要你決定的
- …
```

「先建立的項目」只放使用者給過的內容；還不知道的寫「等你提供 <什麼>」，不要為了填滿而編項目。

代號是大寫英文字母開頭、2 到 10 碼的大寫英數（例如 `WEB`、`MNT`、`INT`），會出現在每一個項目的編號上（`WEB-12`）。取短、好唸、不會變的；之後要改就只能改名稱。

### 3. 分工：網頁上做的與你做的

`kumi` 和權杖做不到這些，請使用者在網頁上做，並在提案的「你要在網頁上做的」逐條寫清楚：

- **建立專案**：選模板、填代號與名稱。正式用的專案**不要勾**「附上範例項目」。
- **加成員**：除了組織的擁有者與管理員，只有專案成員看得到專案；通知也只發給成員。
- **週期與里程碑**：在專案的規劃頁建立（例如維運每個月一個週期）。項目要放進哪個週期，也在網頁上設。
- **個人的檢視**：例如「等客戶」「已過期」的存檔檢視。

你用 `kumi` 做的：照提案改藍圖（照 `kumi` skill 的藍圖流程，`plan` 給使用者看過才 `apply`）、建立項目。

### 4. 建立

使用者同意提案、在網頁上建好專案之後：

1. 先改藍圖，確定類型、狀態、欄位都在，再建項目。順序反過來，項目會缺欄位或類型不存在。
2. 項目先建上層、再建下層：上層建好拿到編號，下層用 `--set parentKey=<上層編號>`。
3. 建完列出每一筆的編號、標題、負責人、到期日，讓使用者對照。

## 記需求

客戶來信、會議結論、需求文件、口頭交代的事，照 `references/capture.md` 整理成項目：放哪個專案、找重複、類型與層級、標題、說明的格式、負責人、日期、資訊不夠時怎麼問，規則都在那裡（Kumi 的 AI 助理也讀同一份）。這裡只寫用 `kumi` 指令時的做法。內容寫不出「怎樣算完成」時，先照「問答」用「模糊的需求」那一套問一輪。

1. **決定專案**之後 `kumi blueprint export -p <代號> --format json`，拿到類型、欄位與選項的 key；`--type`、`--set` 都要用 key。新客戶還不在「客戶」的選項裡時，先照 `kumi` skill 的藍圖流程加一個選項（只加選項不會動到既有資料），再記項目。
2. **找重複**：除了用幾個關鍵字 `kumi search`，也列出同一個客戶還沒完成的項目（`item list --field <客戶欄位>=<選項> --category not_started --category in_progress --category backlog --all --json`），自己看標題。
3. **附件**：截圖、素材、規格檔用 `kumi item attach` 附上，再把附件連結寫進說明（寫法見 `kumi` skill）。附件要先有項目才附得上，所以順序是：建項目 → 附檔 → 用 `item update --set description=…` 補上連結。
4. **優先順序**用 `--set priority=urgent`、`high`…。
5. **先給使用者看**：照「問答」的三段格式。「打算建立的」是一張表，列出要建立的每一筆（專案、類型、標題、上層、負責人、到期日、優先順序、估計、欄位），建議的負責人與日期標「（建議）」。使用者同意後才建立，建完回報編號，並列出記成「待確認」的問題。

## 定期檢視

使用者問進度、問「有什麼卡住」時，看整個專案（不只 `--mine`，除非他只問自己的），找出需要有人動作的項目。日期一律依組織時區換算（見 `kumi` skill）。

| 要找的 | 怎麼找 |
|---|---|
| 已過期 | `--due-to <昨天>`，類別是 `backlog`、`not_started`、`in_progress`（暫停的也算，和網頁的「已過期」一致） |
| 這週到期 | `--due-from <今天> --due-to <這週日>`，類別同上 |
| 等客戶太久 | `--state <在等客戶的狀態 key>`，可以重複給。再對每一筆 `kumi item view <編號> --json`，在 `activity` 裡找最近一筆 `kind` 是 `transitioned`、`toState` 是那個狀態的，它的 `at` 就是開始等的時間 |
| 進行中卻很久沒動 | 類別 `in_progress`，`updatedAt` 超過兩週 |
| 沒有負責人 | 還沒完成的項目裡 `assignee` 是 `null` 的 |
| 沒有到期日 | `--no-due`，類別同已過期 |
| 太大 | 沒有下層，`estimate` 超過 16 小時，或標題看起來包了好幾件事 |

「在等客戶」的狀態不只一個，key 每個專案也不一定一樣：從藍圖裡依名稱與意思找。內建模板有兩個：任務與維運流程的「等客戶」（`waiting_client`），以及接案專案交付流程的「客戶驗收」（`client_qa`）。`activity` 只有最近 10 筆；找不到那筆轉換時，用 `updatedAt` 估，並說「至少等了 N 天」。

回報的格式：

```markdown
## <專案或範圍> 的檢視（<日期>）

### 要催客戶的（N）
- WEB-31 首頁橫幅換成冬季活動版：等了 9 天（負責：<名稱>）

### 已過期的（N）
- …

### 建議
- <具體的動作，例如「WEB-40 拆成三個下層」「WEB-12 沒有負責人，要指派給誰？」>
```

每一類都沒有就寫「沒有」，不要省略標題：使用者要知道你查過了。檢視只讀不寫；建議的修改照 `kumi` skill 的規矩，使用者同意後才做。留言催過、開了追蹤的項目，只代表那個動作做了；事情有沒有解決看項目的狀態，下一次檢視還在就照樣列出來。

### 你看到的是使用者看得到的

檢視出來的只有使用者看得到的項目。`kumi project list --json` 的 `myRole` 是他在那個專案的角色：內建的「執行者」（`contributor`），或藍圖 `roles[]` 裡 `permissions` 只有 `item.read_own`、沒有 `item.read` 的自訂角色，列得出來的只有他負責或建立的。這時在報告開頭寫明「這是你負責或建立的項目，不是整個專案」，不要說「專案沒有過期的項目」。

### 進度的數字

使用者問「做到幾成」「來得及嗎」時：

- **先報個數，再談百分比。** 還沒開始、進行中、完成、取消各幾筆一定算得出來，先給這個。讀完所有分頁（`--all`）再算，並寫明範圍：哪個專案、哪一天讀的。
- **只算最下層的項目。** 有下層的項目不算，不然同一件事上下層各算一次。取消的不放進分母，另外寫有幾筆。
- **要用工時加權，先看估計填了幾成。** 沒填估計的不是 0 小時。最下層的項目大多有 `estimate` 時，才給「完成的估計 ÷ 全部的估計」，並寫出有幾筆沒估；不然只報個數，不要硬湊一個百分比。
- **不要給看起來很準的完成日。** 系統沒有過去的完成速度，也沒有每個人能用的時數，推不出可靠的日期。改成講依據：還剩幾筆、其中幾筆過期或在等客戶、離上線日（里程碑，或最晚的到期日）還有幾天、哪幾筆不動就會趕不上。

## 結案

使用者說案子做完了、要結案時，先檢查、再建議，封存由他決定：

1. **列出還沒結束的項目**（類別 `backlog`、`not_started`、`in_progress`，加 `--all`），請使用者一筆一筆決定：補做完、取消（留紀錄），還是上線後才要做。上線後才要做的，在維運專案開一筆新的，舊的那筆取消、在說明寫上新的編號：項目不能直接搬到別的專案。
2. **還停在「客戶驗收」這類狀態的**，沒有客戶點頭的紀錄（留言、來信）就不要當成驗收過了，問使用者。
3. **回報分四類**：做完的、等客戶驗收的、不做了的、移到維運的。有填工時的話，附上估計與實際（`actual_hours`）各自的加總，以及各有幾筆填了。
4. **都處理完、使用者明確說要封存**，才 `kumi project archive <代號>`。封存之後只能看；之後的小修改記到維運專案。

## 誠實說做不到的

- 一個項目多位負責人：刻意不支援，改用下層任務與「關注」。
- 建立專案、加成員、週期、里程碑、個人檢視：只能在網頁上做。
- 不要假設系統會自動提醒到期或等太久；要提醒，就請使用者定期叫你做「定期檢視」。你自己也一樣：只有被叫到的時候才會跑，不要說「我會持續追蹤」「到時候提醒你」，除非你所在的工具有排程的功能，而且真的替他設好了。
- 項目之間的先後（誰擋誰）：系統沒有這種欄位。上下層是拆解，不代表先後。有前置的事寫在說明裡（「要等 WEB-31 完成才能開始」），並告訴使用者這只是文字：系統不會因此擋狀態，前面的延了後面也不會自己順延，檢視時要自己對。
- 風險清單：系統沒有專門的。「可能會發生的」（風險）和「已經卡住的」（問題）分開講。要持續盯的風險，建議使用者開成一般的項目（有負責人、到期日是下一次要看的日子），他同意才開。
- 每個人的負載：系統沒有每個人能用的時數，也不知道誰請假、誰還有別的事。只能列每個人手上還沒結束的有幾筆、估計加起來幾小時（只算最下層、有填估計的），算不出「負載率」；也不要拿這個數字評斷誰做得好不好。
- 原本承諾的日期：項目只有一個到期日，改了就蓋掉。延過幾次要從活動紀錄看（`item view` 只帶最近 10 筆）；對外承諾的日子請使用者在網頁建成里程碑。
- 沒有週期性的項目：每月的例行工作不會自己長出來。請使用者每個月初叫你建一次（同一套標題，例如「12 月例行：備份檢查」），或在網頁建好新的週期時一起建。
- 工時報表：系統還沒有，要加總就用 `item list --all --json` 讀出 `fields.actual_hours` 自己加。工時是每個項目一個數字，不是按日記的，所以「這個月的工時」只能近似：以到期日落在那個月的項目為準，並在報告裡寫明算的範圍（哪些專案、以哪個日期為準、什麼狀態）。依客戶加總時，維運專案看「客戶」欄位，接案專案一案一個客戶，看專案本身。
