# 內建的模板

在網頁上「新增專案」時選一個模板，模板的藍圖就是新專案藍圖的第 1 版；之後可以照 `pm-tool` skill 的藍圖流程再改。這份是寫的時候的版本，**以網頁上新增專案列出的為準**；名稱、狀態、欄位不一樣時，以專案匯出的藍圖為準（`kumi blueprint export -p <代號> --format json`）。

挑模板的原則：先找流程最接近的，再改差的地方。整個流程都對不上時，從「簡單任務看板」開始，比硬改一個不像的模板簡單。

## 怎麼挑

| 情況 | 模板 |
|---|---|
| 有報價、有上線日的接案建置 | 接案專案 |
| 多個客戶的維護、代管、例行工作 | 客戶維運 |
| 公司內部的事、小團隊的日常 | 簡單任務看板 |
| 產品開發，兩週一個衝刺 | Scrum 衝刺 |
| 產品經理排目標與功能 | 產品路線圖 |
| 收集、確認需求再排進開發 | 需求管理 |
| 測試與客服回報的缺陷 | 缺陷追蹤 |
| 線上服務出事、事後檢討 | 維運與事故 |
| 每次上線前的檢查清單 | 發行與上線檢查 |
| 行銷檔期與內容排程 | 行銷活動與內容行事曆 |
| 設計團隊的設計任務 | 設計專案 |
| 會議的決議與待辦 | 會議與決議追蹤 |

## 各模板

括號裡是 key。狀態依序列出，後面是類別；「限制轉換」表示只允許藍圖裡列出的轉換。

### 接案專案（`agency_project`）

從需求確認到結案的交付流程，客戶以訪客身分參與驗收。

- 類型：需求、需求變更單（走交付流程）；任務（上層是需求或需求變更單）、子任務（上層是任務），兩者走任務流程。
- 交付流程（限制轉換）：需求確認、報價（`not_started`）→ 設計、開發、內部驗收、客戶驗收（`client_qa`，在等客戶）（`in_progress`）→ 結案（`done`）。轉到客戶驗收、結案只有專案經理能做，結案前要填客戶驗收日。
- 任務流程（不限制轉換）：待辦 → 進行中 → 內部驗收 → 等客戶（`waiting_client`）→ 待上線 → 完成，另有暫停（`backlog`）、取消。任務常常跳步，所以不限制。
- 欄位：報價金額（TWD）、客戶驗收日、變更原因、影響程度（單選）、實際工時（`actual_hours`）。
- 檢視：進度看板、需求清單、給客戶看。角色：專案經理、客戶。

### 客戶維運（`client_maintenance`）

所有客戶的修改、問題、資安與例行工作放在同一個專案，每個月一個週期。

- 類型：修改、問題、資安、例行、評估；下層一律是任務。跨好幾個客戶的工作（例如同一個資安修補），每個客戶開一個下層任務。
- 維運流程（不限制轉換）：和接案專案的任務流程一樣，有「等客戶」。
- 欄位：客戶（單選）、實際工時（`actual_hours`）、網址。**客戶的選項是範例，要換成真的客戶**（照 `pm-tool` skill 的藍圖流程改選項）。
- 檢視：進度看板、等客戶、依客戶。週期要在網頁的規劃頁建（每個月一個）。

### 簡單任務看板（`simple_tasks`）

待辦、進行中、完成三個狀態，不限制轉換，適合小團隊與內部的事。

- 類型：任務。
- 欄位：每種型別各一個示範用的欄位（分類、標籤、檢查日、點數、預算、卡住了、參考連結、審查者、摘要、備註）。正式用時，把用不到的拿掉，要加總工時就加 `actual_hours`。

### Scrum 衝刺（`scrum`）

產品開發團隊，兩週一個衝刺。

- 類型：史詩 → 故事 → 任務；缺陷的上層是故事或史詩。四種類型共用一條流程。
- 流程（限制轉換）：待辦 → 進行中 → 審查中 → 完成，另有取消。
- 欄位：驗收條件、嚴重度。衝刺用週期。

### 產品路線圖（`product_roadmap`）

產品經理從目標拆成計畫與功能，依影響與信心排序。

- 類型：目標 → 計畫 → 功能，共用一條流程。
- 流程：構想（`backlog`）→ 規劃中 → 進行中 → 已完成，另有擱置（`canceled`）。
- 欄位：影響、信心、預計季度（都是單選）。

### 需求管理（`requirements`）

需求從訪談、撰寫到確認後排程。

- 類型：需求。
- 流程（限制轉換）：訪談 → 撰寫 → 已確認 → 納入排程（`done`），另有不採納。轉到已確認前要先寫驗收條件。
- 欄位：來源（單選）、提出人、商業價值（單選）、驗收條件。

### 缺陷追蹤（`bug_tracking`）

測試與支援團隊，依嚴重度排優先。

- 類型：缺陷。
- 流程（限制轉換）：新回報 → 已確認 → 修正中 → 待驗證 → 已關閉，另有不處理（重複、無法重現、不打算修）。
- 欄位：嚴重度（單選）、重現步驟、環境、發現版本、修正版本。

### 維運與事故（`incident_ops`）

線上服務的事故，從發生、緩解、檢討到關閉。

- 類型：事故；後續改善（上層是事故）。
- 事故流程（限制轉換）：發生 → 處理中 → 已緩解 → 事後檢討 → 關閉，另有誤報。關閉前要填根本原因。
- 欄位：事故等級（單選）、影響範圍、根本原因、檢討文件連結。

注意：這是「線上服務出事」用的。日常的客戶維護、修改請用客戶維運。

### 發行與上線檢查（`release_checklist`）

每次發行掛上檢查項目，上線前看還有哪幾項沒確認。

- 類型：發行；檢查項目（上層是發行）。
- 發行流程：規劃中（`backlog`）→ 準備中 → 上線中 → 已上線，另有已取消、已回復。檢查流程：待確認 → 已確認，另有不適用。
- 欄位：版本號、環境（單選）、回復計畫。系統不會擋「檢查沒做完就上線」，由人看「未確認的檢查」決定。

### 行銷活動與內容行事曆（`content_calendar`）

行銷檔期與內容排程。

- 類型：活動；內容（上層是活動，也可以單獨存在）。
- 內容流程（限制轉換）：企劃 → 製作 → 審稿 → 排程 → 已發布，另有取消。活動流程：規劃中 → 進行中 → 已結束，另有取消。
- 欄位：通路（多選）、內容形式（單選）、稿件連結。內容的到期日是預計發布日，開始日是開始製作。

### 設計專案（`design_project`）

設計任務從探索、線框、視覺到審查，通過後交付開發。

- 類型：設計任務。
- 流程（限制轉換）：探索 → 線框 → 視覺 → 設計審查 → 交付開發（`done`），另有擱置。
- 欄位：設計稿連結、平台（多選）、審查者（人員）。

### 會議與決議追蹤（`meeting_decisions`）

會議留下決議與待辦，逐項追蹤到完成。

- 類型：會議；決議（上層是會議）；待辦（上層是會議或決議）。
- 會議流程（限制轉換）：預定 → 已開會 → 已整理，另有取消；轉到已整理前要填會議紀錄。決議流程：提案 → 已決議，另有撤回。待辦流程：待辦 → 進行中 → 完成。
- 欄位：會議日期、會議紀錄、決議內容。

會議的待辦常常其實屬於某個案子或維運專案；那種情況直接在那個專案建項目，說明裡寫來自哪一次會議，比另開會議專案好追。
