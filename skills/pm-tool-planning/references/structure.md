# 結構怎麼決定

Kumi 的結構由外到內是：組織 → 專案 → 項目（可以有下層）。每個專案有自己的**藍圖**：項目類型、流程（狀態與轉換）、自訂欄位、檢視、角色。藍圖的格式與修改流程見 `pm-tool` skill 的 `references/blueprint.md`；這份講的是**該設成什麼樣子**。

## 專案怎麼分

一個專案是「一群人、一套流程、一起看進度」的範圍。依工作的**生命週期**分，不依客戶、人或月份分：

| 工作的樣子 | 怎麼放 | 模板 |
|---|---|---|
| 有報價或合約、有上線日、會結束的（建置案、一次性的大改版） | 一案一個專案。結案後封存，之後的小修改歸到維運 | 接案專案 |
| 持續、很多客戶、每件都不大的（維護合約、代管、例行檢查） | 所有客戶放**一個**維運專案，「客戶」是單選欄位，每個月一個週期 | 客戶維運 |
| 公司自己的事（行政、內部系統、招募） | 一個內部專案 | 簡單任務看板 |
| 有固定節奏的產品開發 | 一個產品一個專案 | Scrum 衝刺、產品路線圖 |
| 其他有明確流程的團隊工作（行銷、設計、事故、發行、會議） | 一個團隊或一條產品線一個專案 | 見 `templates.md` |

不要這樣分，以及為什麼：

- **一個客戶一個專案**：大多數客戶一個月只有零到兩件事，會散成幾十個幾乎空的專案，主管看不到全貌、排不出先後。同一個客戶的不同期是不同的合約，本來就該是不同的案子。
- **一個人一個專案（個人看板）**：同一件事會在共用的專案和個人的看板各記一份，最後兩邊對不上。每個人看「我的工作」，跨專案列出自己負責的。
- **一個月一個專案**：月份是**週期**，不是專案。用專案分月份，跨月的事就得搬家。
- **一個大專案裝所有東西**：案子與維運混在一起時，流程不同的事被迫走同一條流程，看板也分不出哪些是有上線日的案子。

## 類型怎麼分

類型決定一個項目走哪一條流程、有哪些欄位。**流程或欄位不同才開新類型**；只是想分類，用單選欄位。

- 「需求」與「任務」流程不同（需求要報價、客戶驗收；任務只是做完）：開兩個類型。
- 「前端任務」與「後端任務」流程與欄位都一樣：同一個類型，加一個「分類」單選欄位，或靠負責人分。
- 「修改」「問題」「資安」流程一樣，但要分開統計、主管想一眼看出是哪一種：開類型也可以，客戶維運模板就是這樣做的。拿不準時，選比較少的類型。

類型越多，建立項目時越容易選錯，篩選也越難用。一個專案三到六個類型通常就夠了。

## 層級與拆解

- 上下層由藍圖的 `itemTypes[].parents` 決定：哪些類型可以掛在哪些類型底下。**類型不能把自己當上層**，任務底下要再拆，就要另一個類型（例如接案專案的「子任務」）。
- 一般兩層就夠（需求 → 任務），最多三層（需求 → 任務 → 子任務）。再深就是項目切得太細，或上層其實應該是一個專案。
- 什麼時候拆下層：
  - 要兩個以上的人做：每人一個下層，各自指派。
  - 超過一兩週做不完：依階段或依可交付的部分拆。
  - 一件事跨好幾個客戶、網站或頁面（例如同一個資安修補要套到五個網站）：每個客戶或網站一個下層，進度各自看得到。
- 進度寫在下層的狀態裡，不要寫在留言裡（「A 站做完了，B 站還沒」）。留言是討論，不是進度表。

## 狀態怎麼設

每個狀態要回答「**這件事現在卡在哪一關、在等誰**」。

- 三到八個狀態。少於三個看不出進度，多於八個大家會分不清、隨便選。
- 等外部的狀態獨立出來：「等客戶」和「內部驗收」分開，主管每天看「等客戶」就知道該催誰。等廠商、等法務也一樣，真的常發生才開。
- 每個狀態的類別要選對，「我的工作」與跨專案的清單只看類別：
  - `backlog`：還不打算做，或暫停（客戶喊停、還沒結束）。仍算未完成，不會從清單消失。
  - `not_started`：排好了，還沒開始。
  - `in_progress`：在做，或在等某個人（等客戶、內部驗收、待上線都是）。
  - `done`：做完了。
  - `canceled`：不做了。保留紀錄，之後有人再提時查得到；不要用刪除代替。
- 轉換（`transitions`）只在真的要擋的地方才列，例如「只有專案經理能結案」「結案前要填客戶驗收日」。沒列轉換時任何兩個狀態都能互相轉；限制越多，大家日常就要多點越多下，小修改常常需要跳步。
- 不同專案裡意思一樣的狀態，名稱、類別、key 盡量一致（內建的接案與維運模板都用 `todo`、`doing`、`internal_review`、`waiting_client`、`to_release`、`done`、`on_hold`、`canceled`），團隊在專案之間切換時不用重新記。

## 欄位怎麼設

自訂欄位是為了**篩選、分組、加總**。不會拿來篩、也不會加總的資訊，寫在說明裡就好。

- 要篩選或分組的用單選（例如「客戶」）。文字欄位沒辦法依值篩，大家拼法也會不一樣。
- 選項的 key 用英文、不會變，顯示名稱（`name`）才寫客戶的真名，之後改名不影響篩選與存好的檢視。中文名稱的客戶，key 用它的英文名或網域的小寫（`acme`、`example_shop`），沒有就用拼音的簡稱；整份清單先給使用者確認。key 規則：小寫英文字母開頭，只有小寫字母、數字、底線，2 到 40 個字元。
- 接案專案一案一個客戶，專案本身就代表客戶，通常不必再加「客戶」欄位。真的要跨專案依客戶篩選時，key 和選項的 key 都跟維運專案用一樣的。
- 要跨專案加總的，每個專案都用**同一個 key**：工時一律是 `actual_hours`（數字，實際小時）；預估用項目本身的「估計」（`estimate`），不另開欄位。
- 人用負責人或人員欄位（`person`），不要用文字寫名字。網址用 `url`。
- 不要開這些欄位：
  - 「進度 %」：進度看狀態與下層完成了幾個，手填的百分比沒人會更新。
  - 「負責人 2」「協作者」：違反一個項目一位負責人；改用下層任務與關注。
  - 「備註」「備註 2」：用說明與留言。
  - 「月份」：用週期。

## 日期、週期與里程碑

- **到期日**：要交出去的那一天。每一項都要有。
- **開始日**：要排期間時才填（開始日到到期日就是一段，行事曆與時間軸會畫成一條）。
- **估計**：預估要幾小時。超過 16 小時又沒有下層的，通常可以再拆。
- **週期**：一段固定的期間，例如維運的每個月、Scrum 的兩週衝刺。在網頁的規劃頁建立，項目放進週期也在網頁上做。
- **里程碑**：對外承諾的日子，例如上線日、驗收日。在網頁的規劃頁建立。

## 從別的工具搬過來時常見的問題

搬之前先看舊的資料有沒有這些情況，提案時一併處理，不要原樣搬過來：

| 舊的樣子 | 搬過來時改成 |
|---|---|
| 一個大看板，群組一半是案子、一半是月份 | 案子各自一個專案；月份變成維運專案的週期 |
| 同一件事在共用看板和個人看板各記一份 | 只留共用專案裡的那一份，每個人看「我的工作」 |
| 一個項目掛兩、三個人 | 指派給真正做的人；其他人改成關注，或拆下層 |
| 一個項目包了很多站、很多頁，進度寫在留言 | 拆成每站、每頁一個下層 |
| 十幾個狀態，意思重疊；分不出在等客戶還是在等自己 | 收斂到上面「狀態怎麼設」的那一套，「等客戶」獨立 |
| 很久沒動、還沒完成的舊項目 | 問使用者：取消（留紀錄）、暫停，還是真的還要做 |

從 monday 搬資料有專用的匯入器（`kumi import monday …`，見 `docs/CLI.md`）；這份 skill 負責決定搬去哪裡，匯入器負責搬。
